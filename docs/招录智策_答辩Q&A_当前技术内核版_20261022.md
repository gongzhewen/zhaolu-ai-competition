# 招录智策答辩 Q&A（当前技术内核版）

日期：2026-10-22

适用架构：中文向量 RAG + 19 类 ONNX 意图路由 + 流式状态反馈

## 〇、先统一答辩口径

### Q1：一句话介绍现在的招录智策。

**A：** 招录智策是面向高校招生管理部门的 AI 数据分析与决策支持系统，核心原则是“模型负责理解和解释，受控工具负责查询与计算，系统负责核验、追溯和拒答”。

**术语卡：**

- **AI 数据分析**：用自然语言、检索、分类和统计工具分析业务数据，而不是只展示固定报表。
- **决策支持**：提供数据、风险提示和模拟结果，不替代正式审批和录取决策。
- **受控工具**：预先定义的查询或计算函数，模型不能自由执行任意 SQL。
- **可追溯**：每个回答能说明使用了哪个工具、哪个参数、哪张表和哪些知识依据。

### Q2：当前技术内核由哪些部分组成？

**A：** 由七个部分组成：

1. 中文 BGE 向量与关键词、字符 n-gram 混合检索。
2. 19 类 ONNX 意图模型。
3. 规则优先、模型修正默认歧义的混合路由。
4. 17 个受控业务工具。
5. MySQL 业务数据、汇总分析和缓存失效机制。
6. SSE 流式状态、心跳、回答超时和向量超时保护。
7. 8 个固定演示问题的受控目录与答辩验收口径。

### Q3：哪些是已经实现的事实？

**A：** 17 个受控工具、中文向量 RAG、19 类意图模型、规则优先混合路由、SSE 心跳、回答超时、向量模型超时、固定演示口径、缓存与汇总自愈、MySQL 真实数据回归均已实现。

### Q4：哪些是已经验证的事实？

**A：** 当前可核实结果：

```text
完整 pytest：73 passed
工具子测试：37 passed
HTTP 问数：18/18
演示问题：8/8（本地测试环境）
MySQL 兼容索引：46/46
数据一致性：通过
汇总自愈：通过
中文向量语义检索：通过
```

模型测试：

```text
标准测试 194 条：准确率 99.48%，Macro F1 99.65%
困难测试 39 条：准确率 87.18%，Macro F1 80.77%
```

### Q5：哪些结论不能说？

**A：** 不能说已经完成真实高校大规模试点；不能把 99.48% 说成所有开放问法的端到端准确率；不能说已经完成向量数据库集群；不能说完成了大语言模型全参数微调；不能保证 2 核 4G 在任意并发下都稳定。

### Q6：为什么 99.48% 和 87.18% 不能混着说？

**A：** 两个数字来自不同测试集。99.48% 是 194 条标准模拟意图分类测试；87.18% 是 39 条困难模拟测试。它们验证的是意图分类，不等于最终业务答案正确率，也不等于真实招生办用户满意度。

**术语卡：**

- **意图分类准确率**：系统把问题分到正确工具类别的比例。
- **端到端准确率**：从用户提问、路由、工具取数、数字核验到最终回答全流程都正确的比例。
- **测试集**：用于评估模型的固定问题集合。
- **模拟数据**：结构与真实数据相似、但不对应真实个人的数据。

## 一、产品定位与使用边界

### Q7：产品到底解决什么问题？

**A：** 招生数据分散、专业名称不统一、统计口径不一致、自然语言问数容易产生幻觉、计划调整缺少可解释模拟工具。系统把这些环节串成一个可追溯的软件流程。

**术语卡：**

- **数据孤岛**：数据分散在 Excel、DBF、业务库和线下表格中。
- **统计口径**：同一指标的范围和算法约定。
- **幻觉**：模型生成看似合理、实际没有数据依据的内容。
- **可解释模拟**：能够说明输入、计算过程和风险来源的沙盘分析。

### Q8：目标用户是谁？

**A：** 高校招生管理部门、计划编制人员、学校管理层、数据治理与信息化部门，以及需要多校部署的招生服务机构。

### Q9：它和普通聊天机器人有什么区别？

**A：** 普通聊天机器人主要生成文字；招录智策必须通过受控工具访问招生数据库。数字、优先级和数据来源由工具产生，系统还要做数字一致性、数据支撑度和边界检查。

### Q10：它和普通 BI 有什么区别？

**A：** BI 主要展示固定指标和图表；本系统支持中文自然语言问数、意图路由、工具选择、知识检索、条件统计、拒答和报告生成，但底层统计仍然是确定性的数据库计算。

**术语卡：**

- **BI（Business Intelligence，商业智能）**：通过报表和图表分析业务数据。
- **自然语言问数**：用户直接用中文提问，由系统转换为数据库查询或受控工具调用。
- **确定性统计**：同样输入得到同样结果的计数、求和、平均等计算。

### Q11：产品不做什么？

**A：** 不替代招生章程审查、政策审批和正式录取；不承诺录取；不批量导出学生隐私；没有知识依据时不编造政策；数据不足时不猜数字。

## 二、当前整体技术架构

### Q12：当前系统分几层？

**A：**

```text
前端交互层
→ FastAPI 接口层
→ Agent 编排层
→ 17 个受控工具层
→ MySQL 与分析汇总层
→ 中文向量 RAG / 知识层
→ Docker、Nginx、宝塔部署层
```

### Q13：前端用了什么技术？

**A：** React 19、Vite、TypeScript、Ant Design、ECharts、React Query、Zustand。

**术语卡：**

- **React**：组件化构建网页界面的 JavaScript 库。
- **Vite**：前端开发和打包工具。
- **TypeScript**：带类型检查的 JavaScript。
- **Ant Design**：企业级 UI 组件库。
- **ECharts**：图表可视化库。
- **React Query**：管理服务端请求的缓存、刷新和加载状态。
- **Zustand**：轻量前端全局状态管理工具。
- **UI**：用户看到并操作的操作界面。

### Q14：后端用了什么技术？

**A：** FastAPI、异步 SQLAlchemy、MySQL 8.0、JWT、RBAC、SSE 和 ONNX Runtime。

**术语卡：**

- **FastAPI**：Python 后端 Web 框架。
- **异步 SQLAlchemy**：数据库访问库，在等待数据库时可以处理其他请求。
- **MySQL 8.0**：当前业务数据库。
- **JWT**：登录后签发的身份令牌。
- **RBAC**：基于角色的访问控制。
- **SSE**：服务器通过长连接向浏览器发送状态事件。
- **ONNX Runtime**：运行 ONNX 模型的推理引擎。

### Q15：一次问答的完整链路是什么？

**A：**

```text
用户问题
→ 中文口语规范化
→ 规则路由与槽位抽取
→ 必要时调用 ONNX 意图模型修正歧义
→ 工具白名单与参数校验
→ 查询 MySQL 或执行确定性计算
→ 中文向量 RAG 检索知识与口径
→ 数字一致性检查
→ 数据支撑度与自查
→ SSE 心跳、最终回答、追问或拒答
→ 记录工具调用和来源
```

### Q16：为什么要有 SSE 流式状态？

**A：** 复杂问题需要模型规划、工具查询和向量检索，前端如果只等待最终结果会以为页面卡住。SSE 每 5 秒发送心跳，前端可以持续显示已等待时间。

**术语卡：**

- **SSE（Server-Sent Events）**：服务器持续向浏览器发送事件。
- **心跳/Heartbeat**：任务仍在运行的状态信号。
- **流式反馈**：不必等完整回答结束才向用户展示状态。

### Q17：系统现在有哪些超时保护？

**A：**

```text
中文向量模型加载/检索超时：20 秒
单次 AI 回答总超时：45 秒
容器 Nginx 代理读写超时：120 秒
后端内存上限：1100 MB
```

向量模型超过 20 秒会回退关键词检索；回答超过 45 秒会返回明确错误事件，不无限挂起。

### Q18：为什么要启动时预热向量模型？

**A：** 中文 Embedding 模型第一次加载需要时间。启动阶段预热可以把首次加载成本从用户首次提问时前移，降低第一次问答长时间等待和网关超时的概率。

### Q19：如果 ONNX 路由模型加载失败怎么办？

**A：** `MlAssistedRouter` 捕获异常并回退规则路由，不让模型加载异常直接导致接口 500 或进程退出。规则路径仍可处理明确的问题。

### Q20：如果中文向量模型失败怎么办？

**A：** `search_knowledge` 将向量提供者标记为不可用，并回退到原有关键词、短语和字符 n-gram 检索。主服务不因模型不可用而整体失效。

### Q21：502 和 504 分别是什么意思？

**A：**

- **502 Bad Gateway**：Nginx 无法从后端得到可用响应，常见于后端进程退出、重启或内存被杀。
- **504 Gateway Timeout**：后端在代理超时时间内没有返回，常见于模型冷加载、外部模型过慢或长任务阻塞。

**术语卡：**

- **网关**：位于浏览器和后端之间的 Nginx 或代理服务。
- **OOM**：内存不足，进程可能被系统杀死。
- **冷加载**：模型或缓存第一次加载产生的额外等待。

### Q22：为什么会退出码 137？

**A：** `137 = 128 + 9`，通常表示进程收到 `SIGKILL`，最常见原因是容器内存超过限制。如果在后端容器内再启动一套 FastAPI/TestClient，会重复加载应用和模型，尤其容易触发 OOM。

### Q23：为什么验证脚本不能和后端同时启动第二套应用？

**A：** 因为容器已经运行了一个 FastAPI 进程，再用 TestClient 启动第二个应用会重复占用 Python、数据库连接和模型内存。验收应优先调用正在运行的后端 HTTP 接口，而不是在同一个容器里再启动一套应用。

## 三、智能体与意图路由

### Q24：规则路由负责什么？

**A：** 识别年份、省份、专业、姓名、分数、性别、报到状态、咨询、漏斗、分数段等明确条件，并选择对应的工具。规则适合稳定、可解释、低延迟的高频问题。

### Q25：19 类意图模型负责什么？

**A：** 将问题分类到 17 个受控工具、能力询问和拒答边界，共 19 类。模型主要用于规则落入默认招生总览时的歧义修正，不负责数字计算。

**术语卡：**

- **意图/Intent**：用户想要完成的任务类别。
- **分类器**：把输入分配到预定义类别的模型或程序。
- **槽位/Slot**：工具参数位置，如年份、省份、专业。
- **默认招生总览**：规则没有命中更具体业务时进入的兜底工具。

### Q26：为什么不让 ONNX 模型覆盖全部规则？

**A：** 规则在明确业务问法上更稳定、可解释，且不会误解“招生计划”为“招生漏斗”。当前采用规则优先、模型修正默认歧义，兼顾稳定性和泛化能力。

### Q27：模型是怎么训练的？

**A：** 基座为 `ernie-3.0-nano-zh`，在 19 类招生意图数据上训练，训练集 1458 条、验证集 194 条、标准测试 194 条、困难测试 39 条。最终导出为 ONNX。

### Q28：为什么用 ONNX，而不是运行时直接用 Paddle？

**A：** ONNX 是部署格式，运行时使用 ONNX Runtime 即可，不需要在业务容器中同时引入完整 Paddle 训练环境，部署更轻、更可控。训练阶段仍使用 Paddle/PaddleNLP。

### Q29：模型准确率是多少？

**A：** 标准模拟测试 194 条准确率 99.48%、Macro F1 99.65%；困难模拟测试 39 条准确率 87.18%、Macro F1 80.77%。这是意图分类指标，不是端到端回答准确率。

### Q30：为什么模型不能直接算人数？

**A：** 大模型生成数字不可重复、不可审计，也无法保证与数据库一致。人数、计划、录取、报到和分数统计必须由受控工具执行确定性计算。

### Q31：工具白名单有什么作用？

**A：** 模型只能从 17 个注册工具中选择，不能任意写 SQL、调用系统命令或访问未授权数据。

### Q32：参数校验检查什么？

**A：** 参数是否存在、类型是否正确、取值范围是否合理、年份/省份/专业是否符合业务、当前用户是否有权限。

### Q33：为什么使用 JSON 结构化输出？

**A：** 程序可以稳定读取意图、工具名、参数、数据来源和限制，避免从自由文本中猜测字段。

### Q34：为什么要低温度？

**A：** 降低模型输出的随机性，使规划和表达更稳定。业务数字仍由工具提供，温度不用于控制统计计算。

### Q35：数据支撑度是什么？

**A：** 回答是否有足够的数据来源、工具结果和知识依据。低于阈值时系统拒答，而不是用语言补全空白。

### Q36：五维自查和 CoVe 是什么？

**A：** 五维自查是回答前对意图、数据依据、数字一致性、安全边界和表达限制进行复核的统称。CoVe 是核验链，强调对结论逐项验证；答辩时不展示模型隐藏的内部思维链，只展示可审计的工具调用和核验结果。

**术语卡：**

- **CoT**：思维链，一种让模型分步推理的技术；不应把隐藏内部推理当作公开证据。
- **CoVe**：Chain of Verification，核验链。
- **置信度**：对结果可靠性的分级或数值估计。
- **阈值**：触发拒答、追问或回退的临界值。

### Q37：系统什么时候追问、什么时候拒答？

**A：**

- 缺少关键年份、指标或筛选条件：`clarify`，追问。
- 问题超出招生业务：`out_of_scope`。
- 涉及学生隐私、保证录取、越权或批量导出：`refuse`。
- 知识库没有政策依据：说明依据不足，不编造。

**术语卡：**

- **Clarify**：追问关键条件。
- **Out-of-scope**：超出业务范围。
- **Refuse**：基于安全或权限拒绝。

### Q38：长期记忆保存什么？

**A：** 保存用户偏好、非敏感业务事实和对话摘要，不保存学生手机号、身份证号、家庭住址等个人身份信息。

**术语卡：**

- **长期记忆**：跨会话保留的非敏感上下文。
- **PII**：可识别个人身份的信息。
- **会话摘要**：压缩后的多轮对话内容。
## 四、中文向量 RAG 与知识库

### Q39：什么是 RAG？

**A：** RAG 是“检索增强生成”，先从知识库找出与问题相关的内容，再让模型或回答模板依据检索结果组织回答。

**术语卡：**

- **Retrieval**：检索。
- **Augmented**：用检索结果增强回答。
- **Generation**：组织或生成自然语言答案。
- **知识块/Chunk**：知识库中可独立检索的一段内容。

### Q40：当前中文向量 RAG 用的是什么模型？

**A：** 使用 `BAAI/bge-small-zh-v1.5` 中文 Embedding，输出 512 维向量，以 ONNX 格式随源码包提供。

**术语卡：**

- **Embedding**：把文本转换成数值向量。
- **余弦相似度**：比较两个向量方向是否接近的指标。
- **ONNX**：跨框架的模型交换和部署格式。
- **向量维度**：每个向量包含的数值个数，当前为 512。

### Q41：混合检索是如何排序的？

**A：** 同时计算关键词/字符 n-gram 的词汇分数和 BGE 的向量相似度，再按权重融合。默认向量权重为 0.55，保留关键词分数以保护年份、专业代码和政策编号等精确匹配。

### Q42：为什么保留字符 n-gram？

**A：** 向量检索擅长语义相近，但对专业代码、年份、缩写和专有名词可能不够精确。字符 n-gram 可以补充字面匹配能力，两者组合比单独使用一种更稳。

**术语卡：**

- **n-gram**：连续 n 个字符或词组成的片段。
- **精确匹配**：字面上完全出现某个词或代码。
- **语义匹配**：意思相近但字面不一定相同。

### Q43：为什么要过滤知识结果？

**A：** 单纯返回前三条会把低相关内容拼进答案。当前会按最高分设置相对阈值，并去除一条内容包含另一条内容的近似重复块，最多保留少量高相关结果。

### Q44：“新生到校比例怎么理解？”现在的标准答案是什么？

**A：** “新生到校比例”通常指实际完成报到的新生人数占已录取新生人数的比例，即：报到人数 ÷ 录取人数 × 100%。它反映录取后的实际到校情况，不等同于招生计划完成率。

**注意：** 这个答案来自受控 FAQ，不再拼接“专业名称归一化”等无关知识。

### Q45：为什么要把演示问题做目录？

**A：** 答辩演示需要稳定、可重复的结果。演示目录固定问题、期望意图、工具和答案边界，避免同一问题因知识检索差异出现不同答案。

### Q46：演示目录会不会把数字写死？

**A：** 不会。概念题和拒答题使用固定口径；咨询、漏斗、分数段、条件统计和官方统计仍实时调用数据库工具，保证数字和当前数据库一致。

### Q47：向量模型加载失败时会发生什么？

**A：** 20 秒超时或加载异常后，系统标记向量提供者不可用，回退关键词检索。页面可以继续工作，但日志会出现 lexical fallback 提示。

### Q48：为什么当前不直接部署大规模向量数据库？

**A：** 当前知识库只有约 81 个知识块，进程内缓存和轻量向量检索已能支撑演示。大规模向量数据库会增加内存、运维和部署复杂度，需要在知识规模和检索评测上升后引入。

**术语卡：**

- **向量数据库**：专门保存和搜索向量的数据库。
- **FAISS**：常用向量相似度检索库。
- **重排/Rerank**：对检索结果再次排序，提高相关性。
- **混合检索**：关键词检索与向量检索组合。

### Q49：RAG 回答有没有引用？

**A：** 政策 FAQ 和知识条目可以返回知识来源或引用字段；如果知识不足，系统应说明没有足够依据。引用不是装饰，而是支持最终结论的证据。

### Q50：当前 RAG 的不足是什么？

**A：** 知识块规模小，尚未接入中文向量数据库和独立重排模型；语义测评集目前较小；真实高校政策语料和用户问法仍需扩充。

## 五、数据导入、治理与数据库

### Q51：系统支持哪些导入格式？

**A：** DBF、Excel、CSV，以及招生计划、录取、报到、分数线和咨询的标准模板。

**术语卡：**

- **DBF**：一种高校历史系统中常见的表格文件格式。
- **Excel**：电子表格文件。
- **CSV**：逗号分隔的纯文本表格格式。
- **标准模板**：规定列名、类型和示例值的上传文件。

### Q52：导入流程是什么？

**A：**

```text
上传
→ 字段识别
→ 字段映射
→ 质量校验
→ 有效行确认
→ 写入数据库
→ 清理缓存
→ 刷新汇总表
→ 记录导入批次和审计
```

### Q53：什么是字段映射？

**A：** 把上传文件中的源字段对应到系统标准字段，例如将“考生姓名”映射到学生姓名字段。这样不同学校的表格可以进入统一分析口径。

**术语卡：**

- **源字段**：上传文件中原来的列名。
- **标准字段**：系统内部统一使用的列名。
- **别名**：同一字段或专业的其他写法。
- **必填字段**：缺少后无法完成导入或识别的字段。

### Q54：数据质量检查包括什么？

**A：** 必填检查、类型检查、范围检查、重复检查、枚举值检查和业务口径检查。

**术语卡：**

- **枚举值**：只允许固定几个取值的字段。
- **唯一性约束**：同一记录不能重复。
- **数据质量**：数据是否完整、准确、一致和符合业务规则。

### Q55：专业名称归一是什么？

**A：** 将“计科”“计算机”“计算机科学与技术”等不同写法映射到标准专业，避免跨省和跨年度统计被拆开。

### Q56：数据库中的六个逻辑域是什么？

**A：**

- `dim`：维度，如学校、专业、省份、年份。
- `fact`：事实，如计划、录取、成绩、志愿、报到。
- `gov`：治理，如字段映射和质量问题。
- `ai`：会话、知识、记忆和反馈。
- `sys`：用户、角色和审计。
- `analytics`：汇总分析结果。

### Q57：分析汇总表和汇总自愈是什么？

**A：** 汇总表提前保存年度、省份、专业等聚合结果，提高驾驶舱查询速度。查询前比较基础表与汇总表的计划、录取总量，不一致时刷新汇总并重新查询。

**术语卡：**

- **汇总表**：保存预计算聚合结果的表。
- **自愈**：系统发现不一致后自动触发修复。
- **故障注入**：故意制造数据缺口，验证系统能否发现并恢复。

### Q58：数据更新后如何处理缓存？

**A：** 导入、计划修改或专业映射变化后清空相关工具缓存、规划器缓存、知识检索缓存并刷新汇总，防止页面和智能体读取旧数据。

**术语卡：**

- **L1 缓存**：应用进程内缓存。
- **Redis**：可选共享缓存。
- **TTL**：缓存生存时间。
- **缓存失效**：数据变化后使旧缓存不再生效。

### Q59：为什么没有统一使用物理外键？

**A：** 批量导入、迁移和年度重建会受到外键顺序限制。项目通过唯一键、索引、事务、服务校验和一致性脚本保障完整性，这是工程取舍，不代表外键没有价值。

### Q60：系统如何保证可追溯？

**A：** 通过工具调用参数、数据来源、导入批次、审计日志和回答自查记录，追踪数字和操作来自哪里。

**术语卡：**

- **审计日志**：记录谁在何时做了什么。
- **数据血缘**：数据从源文件到最终指标的转换路径。
- **事务**：一组要么全部成功、要么全部回滚的数据库操作。

## 六、17 个受控工具与核心功能

### Q61：17 个工具可以怎样分组？

**A：**

```text
招生分析：admissions_overview、source_overview、candidate_profile
成绩与志愿：subject_scores、major_choices、score_band_statistics
录取与报到：official_admission_stats、enrollment_funnel
咨询与政策：consultation_overview、policy_faq
学生与画像：student_lookup、student_statistics、medical_summary
智能决策：forecast、anomaly_detection、plan_simulation
治理与其他：major_alias_lookup
```

### Q62：当前三个重点分析工具是什么？

**A：** `consultation_overview` 查询咨询渠道和转化；`enrollment_funnel` 查询计划、录取、报到漏斗；`score_band_statistics` 查询指定科目的分数段分布。

### Q63：条件统计如何工作？

**A：** 例如“政治考了66分的人有多少”，系统抽取年份、科目和分数条件，调用 `student_statistics` 进行确定性聚合，而不是让模型直接数数。

### Q64：招生驾驶舱做什么？

**A：** 展示年度计划、录取、完成率、生源和报到等指标，并默认选择最近年份，避免把不同年份直接相加。

### Q65：AI 数据洞察做什么？

**A：** 对考生画像、成绩、志愿、生源和计划做多维分析，输出结构、趋势、差异和异常，而不是只显示原始数字。

### Q66：异常检测做什么？

**A：** 检查计划、录取、完成率、志愿热度和报到变化，识别高风险专业并提示人工复核。异常不是自动结论。

### Q67：预测与计划沙盘做什么？

**A：** 预测根据历史数据提供趋势参考；计划沙盘在不修改正式计划的前提下模拟增减计划后的录取、完成率和风险变化。

**术语卡：**

- **情景模拟**：设置不同参数，观察可能结果。
- **基线方案**：用于比较的原始方案。
- **趋势预测**：根据历史数据推测未来方向。

### Q68：AI 报告中心做什么？

**A：** 复用工具数据、指标口径和知识解释生成 DOCX/PDF 报告，提供预览、表格和分析内容。

### Q69：用户、角色和权限如何协同？

**A：** 用户属于角色，角色拥有权限，权限限制学校范围、指标范围和学生个人档案。学生个体查询只允许超级管理员。

### Q70：多学校如何隔离？

**A：** 通过学校上下文、用户学校范围、后端查询条件和租户级数据隔离。前端隐藏按钮不能代替后端权限校验。
## 七、测试、性能与故障排查

### Q71：当前自动化测试有哪些？

**A：**

```text
pytest：73 passed
工具子测试：37 passed
HTTP 问数与意图回归：18/18
演示问题本地验收：8/8
MySQL 兼容索引：46/46
数据一致性：通过
汇总自愈：通过
中文向量 RAG：通过
流式心跳与超时：通过
```

### Q72：模型测试集规模是多少？

**A：** 19 类训练 1458 条、验证 194 条、标准测试 194 条、困难测试 39 条。测试数据是构造和模拟数据。

### Q73：性能指标有哪些？

**A：** 本机实测 ONNX 意图模型 P50 约 3.08 ms、P95 约 3.60 ms、P99 约 3.97 ms。中文向量 RAG 首次查询约 3356.83 ms，搜索缓存命中 P95 约 27.09 ms。以上不是服务器并发压测结果。

**术语卡：**

- **P50**：中位延迟。
- **P95**：95% 的请求不超过该耗时。
- **P99**：99% 的请求不超过该耗时。
- **缓存命中率**：请求直接从缓存返回的比例。
- **并发**：系统同时处理的请求数。

### Q74：答辩前怎样验证 8 个演示问题？

**A：** 优先在浏览器页面逐题演示，观察意图、工具来源、答案内容和位置。当前本地测试环境已通过 8/8；由于验收脚本会在测试中启动应用，不建议在内存受限的后端容器里再运行第二套 TestClient。

### Q75：为什么运行验收脚本会出现 137？

**A：** `137` 通常是 `SIGKILL`，容器内存超限是常见原因。后端已经在容器中运行，再启动一套完整应用和模型会重复占用内存。服务器上应使用浏览器或轻量 HTTP 请求验证，不要把 TestClient 当作容器内巡检工具。

### Q76：遇到 502 或 504 应该先查什么？

**A：**

```text
1. docker compose ps
2. docker compose logs --tail=300 backend
3. docker inspect ... --format 'OOMKilled={{.State.OOMKilled}} ExitCode={{.State.ExitCode}}'
4. 检查模型文件是否存在于容器内
5. 检查 RAG/ONNX 超时与内存配置
```

当前运行版本提供 20 秒向量超时、45 秒回答超时、SSE 心跳、模型异常回退和 1100 MB 后端内存上限。

### Q77：知识检索如何避免把无关内容拼进回答？

**A：** 当前使用固定 FAQ、相关度阈值和近似重复过滤。没有固定条目时，只保留与最高分足够接近的知识块，并去除内容互相包含的重复块，避免把“专业名称归一化”等低相关内容拼入报到政策回答。

### Q78：为什么不能报告一个统一的“智能体准确率”？

**A：** 意图准确率、工具选择准确率、数字正确率、RAG 忠实度、拒答准确率和最终回答满意度是不同指标。当前公开的 99.48% 和 87.18% 只表示意图分类测试结果。

### Q79：目前最重要的技术缺口是什么？

**A：** 真实或脱敏招生问法评测集不足；中文向量知识块规模较小；没有独立重排器；困难测试只有 39 条；2 核 4G 尚未完成正式并发压测。

## 八、创新点与差异化

### Q80：项目最准确的创新表述是什么？

**A：** 面向招生场景的“可信问数闭环”：把中文语义检索、规则与 ONNX 意图路由、17 个受控工具、数据自愈、数字核验、RAG、拒答边界和 SSE 状态反馈组合成可执行流程。

### Q81：没有原创基础算法，能说有创新吗？

**A：** 可以说应用创新、架构创新和工程创新，不能说提出了全新的基础大模型算法。竞赛关注 AI 算法工程化落地，项目的价值在于把算法、数据治理和招生业务约束闭环。

**术语卡：**

- **基础算法**：相对底层、通用的算法创新。
- **应用创新**：将已有算法用于特定场景并解决实际问题。
- **工程化**：把原型变成可部署、可测试、可维护的软件。

### Q82：与通用大模型直接问答相比，优势是什么？

**A：** 数字由数据库工具返回，回答带数据来源，数字可核验，知识不足时可拒答，意图路由和权限边界可控。优势不是模型更大，而是业务事实更可信。

### Q83：与普通 BI 相比，优势是什么？

**A：** 支持中文问数、意图识别、工具编排、知识检索、拒答和报告生成，同时保留 BI 式确定性统计。自然语言只是入口，数字计算仍然确定。

### Q84：如何描述应用价值而不编造效果？

**A：** 可以说预期减少跨表统计时间、降低口径不一致、降低人员学习报表工具成本；真实节省时间、错误率下降和用户满意度必须等真实试点后再量化。

### Q85：市场分析怎么写？

**A：** 高校招生管理存在数据多源、统计频繁和政策口径复杂的需求；项目采用 MySQL、规则快路径、可选向量模型和容器化部署，适合资源有限、先小范围验证的学校。市场规模不能凭空编数字。

### Q86：当前最大不足和未来规划是什么？

**A：** 近期补真实/脱敏评测集和 RAG 消融实验；中期接入中文混合检索、重排和多校租户隔离；长期扩展预测模型、更多业务规则和真实试点。

## 九、8 个演示问题的标准口径

### Q87：新生到校比例怎么理解？

**A：**

> 它通常指实际完成报到的新生人数占已录取新生人数的比例，即：报到人数 ÷ 录取人数 × 100%。它反映录取后的实际到校情况，不等同于招生计划完成率。

展示重点：固定 FAQ、中文语义理解、去除无关知识。

### Q88：2026年咨询渠道转化率怎么样？

**A：** 应调用 `consultation_overview`，展示咨询数、转化数和转化率，并说明渠道口径。

展示重点：咨询渠道、转化率和专项分析工具。

### Q89：2026年招生漏斗和报到流失情况怎么样？

**A：** 应调用 `enrollment_funnel`，按“计划 → 录取 → 报到”展示人数、录取完成率、报到率和录取后流失人数。

展示重点：阶段漏斗与报到转化。

### Q90：2026年政治分数段分布怎么样？

**A：** 应调用 `score_band_statistics`，按十分段展示政治成绩人数和平均分。

展示重点：分数段统计、科目槽位和表格。

### Q91：政治考了66分的人有多少？

**A：** 应调用 `student_statistics`，按年份、考试科目和分数条件聚合人数。

展示重点：条件聚合，不是分数段，也不是单条学生档案。

### Q92：2026年官方招生统计是多少？

**A：** 应调用 `official_admission_stats`，回答普通招生计划、普通录取、专升本和总录取等官方统计指标。

展示重点：官方统计与招生总览、漏斗工具的区别。

### Q93：今天天气怎么样？

**A：** 应进入 `out_of_scope`，明确说明该问题超出招生业务范围。

展示重点：不为了显得智能而回答无关问题。

### Q94：把所有学生手机号导出来。

**A：** 应进入 `refuse`，明确拒绝批量导出个人敏感信息，并说明隐私与权限边界。

展示重点：PII、RBAC 和安全拒答。

# 招录智策最终提交总体答辩 Q&A

日期：2026-10-22

口径：只描述当前系统具备什么、如何工作、验证到哪一步；不做版本变化对比。

## 一、项目设计

### Q1：招录智策是什么？

**A：** 招录智策是面向高校招生管理部门的 AI 数据分析与决策支持系统。用户可以直接用中文询问招生计划、录取、生源、成绩、志愿、咨询、报到和异常风险，系统通过受控工具查询数据库并给出可追溯回答。

**关键术语：**

- **AI 数据分析**：用自然语言、检索和统计工具分析数据。
- **决策支持**：提供分析和风险提示，不替代正式审批与录取决策。
- **可追溯**：能查到回答使用的工具、参数、数据表和知识依据。

### Q2：项目主要解决哪些业务问题？

**A：** 解决五类问题：招生数据来源分散；专业名称和统计口径不统一；跨表统计依赖人工；计划调整缺少模拟工具；大模型直接问数容易产生无依据数字。

### Q3：目标用户是谁？

**A：** 高校招生管理部门、计划编制人员、学校管理层、数据治理与信息化部门，以及需要多学校部署的招生服务机构。

### Q4：项目的核心设计原则是什么？

**A：** “模型负责理解和解释，受控工具负责查询与计算，系统负责核验、追溯和拒答”。大模型不直接编造业务数字，业务事实必须来自数据库工具。

### Q5：产品边界是什么？

**A：** 系统提供统计、分析、风险提示和模拟建议，不替代招生章程审查、政策审批和正式录取；不承诺录取；不绕过权限导出个人隐私；没有数据依据时不猜数字。

### Q6：它与普通聊天机器人有什么区别？

**A：** 普通聊天机器人主要生成自然语言；本系统先把问题路由到 17 个受控工具之一，再查询 MySQL 或执行确定性统计。模型可以解释结果，但不能自由写 SQL 或自行计算业务数字。

### Q7：它与普通 BI 有什么区别？

**A：** BI 以固定报表和人工筛选为主；本系统支持中文问数、意图识别、工具编排、知识检索、条件统计、拒答和报告生成。底层统计仍是确定性的 BI 式计算。

### Q8：项目最有价值的创新是什么？

**A：** 面向招生场景的“可信问数闭环”：中文语义检索、规则与 ONNX 意图路由、受控工具、专业名称归一、数据自愈、数字核验、RAG 和拒答边界共同组成可执行流程。答辩时不应宣称提出了全新的基础大模型算法。

## 二、整体架构

### Q9：整体架构分几层？

**A：**

```text
前端交互层
→ FastAPI 接口层
→ Agent 编排层
→ 17 个受控工具层
→ MySQL 与分析汇总层
→ 中文向量 RAG / 知识层
→ Docker、Nginx、宝塔部署层
```

### Q10：前端采用什么技术？

**A：** React 19、Vite、TypeScript、Ant Design、ECharts、React Query 和 Zustand。

**简要解释：**

- **React**：组件化网页界面库。
- **Vite**：前端开发与构建工具。
- **TypeScript**：带类型检查的 JavaScript。
- **Ant Design**：企业级 UI 组件库。
- **ECharts**：图表可视化库。
- **React Query**：管理接口请求和缓存。
- **Zustand**：管理跨页面前端状态。

### Q11：后端采用什么技术？

**A：** FastAPI、异步 SQLAlchemy、MySQL 8.0、JWT、RBAC、SSE 和 ONNX Runtime。

**简要解释：**

- **FastAPI**：Python 后端接口框架。
- **SQLAlchemy**：数据库访问层。
- **异步**：等待数据库时可处理其他请求。
- **JWT**：登录令牌。
- **RBAC**：基于角色的权限控制。
- **SSE**：服务器向浏览器持续推送状态。
- **ONNX Runtime**：运行意图模型。

### Q12：数据层如何划分？

**A：**

```text
dim        学校、专业、省份、年份等维度
fact       计划、录取、成绩、志愿、报到等事实
gov        字段映射、别名和质量问题
ai         会话、知识、记忆和反馈
sys        用户、角色和审计
analytics  汇总分析
```

### Q13：接口层承担什么职责？

**A：** 负责登录认证、参数校验、文件上传、权限判断、调用 AgentService、返回图表/表格和推送流式状态。

### Q14：权限如何设计？

**A：** 用户属于角色，角色拥有权限，权限限制学校范围、功能范围和学生个人档案。学生个体查询只允许超级管理员，不能只靠前端隐藏按钮。

### Q15：为什么使用 SSE？

**A：** 复杂问数需要路由、工具查询和知识检索。SSE 每 5 秒发送 heartbeat，前端可以持续显示已等待时间；最终答案通过 `answer` 事件发送。

### Q16：部署架构是什么？

**A：** Docker Compose 组织 MySQL、FastAPI 后端和 Nginx 前端；宝塔负责公网域名、反向代理和 HTTPS。前端容器通过 `/api` 转发到后端。

### Q17：如何支持多学校？

**A：** 通过学校上下文、用户学校范围、后端查询条件和权限隔离。更完整的多实例与独立数据面属于扩展方向。

### Q18：2 核 4G 如何控制资源？

**A：** 使用单后端 Worker、MySQL 小内存参数、Nginx 静态前端、规则快路径和可选模型服务；当前容器上限约为 MySQL 1200 MB、后端 1100 MB、Nginx 128 MB。正式并发上限仍需压测。

## 三、智能体设计

### Q19：本项目的 Agent 是什么？

**A：** 它不是任意执行代码的聊天机器人，而是负责“理解问题、选择工具、填写参数、读取结果、核验并输出”的软件编排器。

### Q20：规则路由负责什么？

**A：** 识别年份、省份、专业、姓名、科目、分数、报到状态、咨询、漏斗和分数段等条件，并选择明确工具。规则适合高频、稳定、可解释的问题。

### Q21：19 类 ONNX 意图模型负责什么？

**A：** 将问题分类到 17 个业务工具、能力询问和拒答边界，共 19 类。它用于修正规则进入默认招生总览时的歧义，不负责数字计算。

### Q22：规则和模型怎样组合？

**A：** 采用规则优先：规则命中明确工具时保留规则；规则落入默认招生总览时，模型以置信度为参考修正意图；模型异常时回退规则。

### Q23：什么是 Tool Calling？

**A：** 模型或规划器输出“调用哪个工具、参数是什么”，系统校验后执行工具。模型只能从白名单中选择，不能执行自由 SQL 或系统命令。

### Q24：为什么必须有参数校验？

**A：** 防止模型填错年份、专业、省份或绕过权限。参数校验检查类型、范围、业务合法性和当前用户权限。

### Q25：为什么使用结构化输出？

**A：** 规划器输出 JSON，回答包含意图、数据来源、工具调用、自查和限制。程序可以稳定解析，不依赖从自由文本中猜字段。

### Q26：模型温度如何设置？

**A：** 规划使用较低温度，减少随机性和工具漂移。业务统计仍然确定计算，不靠温度控制。

### Q27：回答前如何核验？

**A：** 检查意图、工具结果、数字一致性、数据来源、安全边界和回答完整性，并计算数据支撑度。支撑度不足时拒答或追问。

### Q28：系统如何区分追问、越界和拒答？

**A：**

- 缺少关键条件：`clarify`，向用户追问。
- 问题不属于招生业务：`out_of_scope`。
- 涉及隐私、越权、保证录取或批量导出：`refuse`。
- 政策知识不足：说明依据不足，不编造。

### Q29：长期记忆保存什么？

**A：** 保存用户偏好、非敏感业务事实和对话摘要，不保存学生手机号、身份证号、家庭住址等 PII。

### Q30：流式问答怎样避免长时间无响应？

**A：** 后端每 5 秒发送 heartbeat；向量模型加载最多等待 20 秒；整次回答最多 45 秒；Nginx 读写超时 120 秒。模型失败时回退规则或关键词检索。

### Q31：8 个演示问题如何保持稳定？

**A：** 通过 `demo_catalog` 固定问题、期望意图、工具和关键回答边界。概念题使用固定口径，数字题仍实时调用工具，避免写死数字后与数据库不一致。
## 四、RAG 与知识库

### Q32：什么是 RAG？

**A：** RAG 是“检索增强生成”：先从知识库检索与问题相关的内容，再基于检索结果生成或组织回答。它让回答有知识依据，而不是完全依赖模型记忆。

### Q33：当前使用什么中文向量模型？

**A：** 使用 `BAAI/bge-small-zh-v1.5`，输出 512 维语义向量，并以 ONNX 格式随源码包提供。

**简要解释：**

- **Embedding**：把文本转换成数值向量。
- **向量相似度**：衡量两段文本语义是否接近。
- **ONNX**：模型部署格式。
- **512 维**：每个文本向量包含 512 个数值。

### Q34：当前检索方式是什么？

**A：** 中文 BGE 向量与关键词、短语、字符 n-gram 混合检索。向量负责语义相近，关键词负责年份、代码、专业和专有名词的精确匹配。

### Q35：怎样避免无关知识混入答案？

**A：** 当前使用固定 FAQ、相对相关度阈值和近似重复过滤。没有固定条目时，只保留与最高分足够接近的内容，并去除一条内容包含另一条内容的重复块。

### Q36：知识不足时怎么做？

**A：** 如果没有知识依据或相关政策，系统说明依据不足，不凭空生成政策结论。引用和知识来源是回答证据的一部分。

### Q37：中文向量 RAG 当前有哪些边界？

**A：** 当前知识库约 81 个知识块，采用进程内索引，没有独立向量数据库和重排模型；语义评测集仍需扩大；真实高校政策语料需要继续补充。

## 五、数据治理与业务功能

### Q38：支持哪些导入格式？

**A：** DBF、Excel、CSV，以及招生计划、录取、报到、分数线和咨询等标准模板。

### Q39：数据质量检查包括什么？

**A：** 必填、类型、范围、枚举、重复和业务口径检查。问题数据不能直接进入智能分析。

### Q40：专业名称归一是什么？

**A：** 把“计科”“计算机”“计算机科学与技术”等不同写法映射到标准专业，保证跨省、跨年度统计口径一致。

### Q41：汇总表和汇总自愈是什么？

**A：** 汇总表保存预计算的年度、省份和专业聚合结果；查询前比较基础表与汇总表的计划、录取总量，不一致时刷新并重新查询。

### Q42：数据变化后怎样避免旧缓存？

**A：** 导入、计划修改或专业映射变化后清理工具缓存、规划器缓存、知识检索缓存，并刷新汇总结果。

### Q43：当前有哪些业务工具？

**A：** 共 17 个，覆盖招生总览、生源、考生画像、单科成绩、专业志愿、体检、预测、官方统计、专业别名、学生档案、学生条件统计、异常检测、计划沙盘、政策问答、咨询、招生漏斗和分数段。

### Q44：三个重点分析工具是什么？

**A：** `consultation_overview` 分析咨询渠道和转化；`enrollment_funnel` 分析计划、录取、报到漏斗；`score_band_statistics` 分析指定科目的分数段分布。

### Q45：条件统计怎样保证正确？

**A：** 系统抽取年份、性别、专业、省份、科目、分数和报到状态等槽位，调用 `student_statistics` 做确定性聚合，而不是让模型自行数数。

### Q46：AI 报告中心做什么？

**A：** 复用工具数据、统计口径和知识解释生成 DOCX/PDF 报告，提供预览、表格和分析内容。

### Q47：学生隐私如何保护？

**A：** 学生个体查询仅允许超级管理员；聚合统计与个体查询分离；PII 不进入外部模型或长期记忆；批量导出隐私数据被拒绝。

## 六、测试、性能与部署

### Q48：当前测试证据是什么？

**A：**

```text
pytest：73 passed
工具子测试：37 passed
HTTP 问数与意图回归：18/18
8 个演示问题 HTTP 验收：8/8
MySQL 兼容索引：46/46
数据一致性：通过
汇总自愈：通过
中文向量 RAG：通过
流式心跳与超时：通过
```

### Q49：意图模型的测试结果是多少？

**A：** 标准模拟测试 194 条准确率 99.48%、Macro F1 99.65%；困难模拟测试 39 条准确率 87.18%、Macro F1 80.77%。它是意图分类结果，不是端到端回答准确率。

### Q50：当前性能如何？

**A：** 本机 ONNX 意图模型 P50 约 3.08 ms、P95 约 3.60 ms、P99 约 3.97 ms；中文向量 RAG 首次查询约 3356.83 ms，搜索缓存命中 P95 约 27.09 ms。服务器并发需要单独压测。

### Q51：502、504 和退出码 137 分别怎么排查？

**A：**

- 502：后端退出、重启或无法连接。
- 504：后端超过网关等待时间。
- 137：进程收到 SIGKILL，常见原因是 OOM。
- 当前系统有 20 秒向量超时、45 秒回答超时和 5 秒 SSE 心跳。
- 验收脚本应通过 HTTP 调用已运行的后端，不应在容器内再启动第二套完整应用。

### Q52：源码部署方式是什么？

**A：** Docker Compose 启动 MySQL、后端和 Nginx；宝塔设置反向代理与 HTTPS。模型通过 Dockerfile 打入后端镜像，更新模型后必须重新构建后端。

### Q53：答辩前要检查什么？

**A：**

```text
1. 登录正常
2. 健康接口正常
3. capabilities 显示 17 个工具
4. 中文向量 RAG 开启
5. ONNX 路由开启
6. 8 个演示问题逐题通过
7. 手机端页面可操作
8. 审计日志可打开
```

## 七、不足与展望

### Q54：当前最重要的不足是什么？

**A：** 真实高校试点不足；端到端评测集不足；困难意图测试只有 39 条；中文向量知识块规模较小；没有独立重排模型；2 核 4G 尚未完成正式并发压测。

### Q55：未来规划是什么？

**A：** 近期补真实或脱敏问法评测集，增加 RAG 混合检索和重排评测；中期加强多学校租户隔离、并发和监控；长期扩展更多招生业务规则、预测模型和真实试点。

### Q56：如果评委让你用三句话总结，怎么说？

**A：** 第一，招录智策把招生数据、专业口径和自然语言问数整合为一个可追溯的智能应用。第二，系统采用中文向量 RAG、规则与 ONNX 混合路由、17 个受控工具和确定性统计，避免大模型直接编造数字。第三，系统已经通过工具、HTTP 问数、数据一致性和 8 个演示问题的自动化验收，真实高校试点和端到端大规模评测仍在后续推进。

### 标准答案示例

**新生到校比例：**

> 它通常指实际完成报到的新生人数占已录取新生人数的比例，即：报到人数 ÷ 录取人数 × 100%。它反映录取后的实际到校情况，不等同于招生计划完成率。

**天气问题：**

> 该问题超出招生业务范围。系统主要回答招生计划、录取、成绩、志愿、生源、报到、异常、预测、计划沙盘和政策问题。

**批量导出手机号：**

> 该请求涉及学生个人敏感信息，不能提供批量导出。请使用聚合统计或经过授权的学生管理功能。

## 九、最后背诵版

1. 招录智策是面向高校招生管理部门的 AI 数据分析与决策支持系统。
2. 核心原则是模型理解和解释、工具查询计算、系统核验追溯。
3. 系统有 17 个受控工具，覆盖招生、生源、成绩、志愿、咨询、报到、预测和报告。
4. 中文 RAG 使用 BGE 向量与关键词/字符 n-gram 混合检索。
5. 向量模型失败时回退关键词检索，主服务不整体失效。
6. 19 类 ONNX 意图模型用于歧义修正，规则仍然优先。
7. 标准模拟意图测试准确率 99.48%，困难模拟测试 87.18%，都不是端到端准确率。
8. 问答链路有 SSE 心跳、20 秒向量超时、45 秒回答总超时和 120 秒 Nginx 超时。
9. 8 个演示问题有固定验证口径，数字题仍实时从数据库工具取数。
10. 真实高校试点、端到端准确率和大规模并发仍待验证，答辩时不夸大。

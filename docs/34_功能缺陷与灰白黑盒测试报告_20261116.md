5. 多轮追问虽然显示“使用了上下文”，但学生姓名槽位仍会丢失，最终要求重新提供姓名。
6. 多学校数据面目前只完整接入智能体链路，普通 UI/API 仍主要使用默认数据库；多学校场景下存在串校风险。

### 3.8 DBF 清理逻辑审计

`_clear_business_data()` 会执行：

```sql
TRUNCATE TABLE
    fact.admission_summary,
    fact.admission_record,
    fact.score_line,
    fact.consultation,
    fact.channel_touch,
    fact.source_quality,
    fact.metric_snapshot,
    fact.plan,
    fact.candidate_profile,
    fact.exam_subject_score,
    fact.major_choice,
    fact.candidate_resume,
    fact.medical_summary,
    dim.region,
    dim.policy,
    dim.channel,
    dim.plan_type,
    dim.batch,
    dim.subject,
    dim.major,
    dim.province,
    dim.year,
    dim.school
RESTART IDENTITY CASCADE
```

还会清空：

- `gov.import_record`
- `gov.etl_job`
- `gov.data_issue`
- `ai.feedback`
- `ai.tool_call`
- `ai.message`
- `ai.conversation`

`POST /data/dbf/imports/{batch_id}/normalize` 的 `clear_existing` 默认值为 `true`，前端会弹出确认框，然后明确发送：

```json
{"clear_existing": true}
```

风险：

1. 解析或后续写入失败时，先前的数据已经被 `TRUNCATE`。
2. MySQL `TRUNCATE` 具有隐式提交语义，普通的 ORM `rollback()` 不能恢复被清空的数据。
3. 清理是全局的，不是按学校或按批次范围。
4. 同时清空 AI 会话和反馈，可能让审计/反馈链路丢失。
5. 没有自动备份、暂存库、预校验全通过后再切换的原子发布流程。

因此这不是普通的“覆盖导入”，而是高风险的全库重建操作。


测试：


- 意图：`admissions_statistics`
- 参数：`group_by=major_group`
- 表格列只有“学院、计划数”

- 系统实际只回答了“按学院统计”。

- 正确行为应是明确提示当前只支持一个主分组维度，并要求用户选择学院或专业，而不是直接给出缩小范围的答案。

## 六、缺陷清单

### P0：上线前必须处理

#### P0-1 未登录可读取招生分析和预测数据

证据：

- 未携带 Token 的 `GET /analytics/admissions/overview?year=2026` 返回 200，并返回约 15 KB 实际数据。
- 未携带 Token 的 `POST /analytics/simulate` 和 `POST /forecast/run` 返回 200。
- 路由文件没有 `require_permission` 或 `get_current_user` 依赖。
- Nginx 将 `/api/` 原样代理到 backend。

影响：

- 任何能访问 Web 端口的人，即使未登录，也能读取招生计划、录取、生源、异常和预测。
- 如果服务绑定到公网或大网，属于数据越权/泄露。

#### P0-2 DBF 归一化存在不可回滚的数据丢失风险

证据：

- `clear_existing` 默认 `true`。
- 处理前执行 `TRUNCATE` 全部业务表、维度表和 AI 对话/反馈表。
- `TRUNCATE` 具有隐式提交语义，之后发生解析或写入异常时不能依靠普通事务回滚恢复。
- 清理范围是全局的，不是按学校/批次范围。

影响：

- 一次格式错误、模型/数据库异常或导入中断，就可能让系统变成空库。
- 前端确认框只能降低误操作概率，不能消除失败后不可恢复的问题。

### P1：功能正确性和数据隔离

#### P1-1 交叉表请求被静默降级

“学院 + 专业”请求返回了单维度学院统计，属于答非所问；应澄清或明确拒答。

#### P1-2 年度范围不正确

- “2024到2026”返回 2022—2026 全部年度。
- “近五年”只返回 2026。
- 官方统计文本把 2022—2026 的数据标成“2024—2026”。

#### P1-3 多轮上下文未恢复学生姓名

解析日志显示 `context_resolution.used=true`，但槽位仍为 `missing_required=["student_name"]`，导致第二轮无法继续。

#### P1-4 多学校隔离只覆盖智能体链路

普通 analytics、plans、reports、quality、students 等接口仍使用默认数据库；plans 写死第一所学校。多学校模式下可能出现读错库、写错校或跨校聚合。

#### P1-5 默认测试门禁不能无提示通过

- 不传 `-Vector` 时测试和脚本配置互相矛盾，出现假失败。
- `run_full_regression.ps1` 依赖外部 `PYTHON_EXE` 或项目 `.venv`，当前没有自动定位到实际虚拟环境。
- pytest 到达 100% 后不退出，CI 可能永远挂起。

#### P1-6 调剂率等少量指标仍依赖滞后的 admission_summary

`admission_summary` 每年都比 `admission_record` 少 7—59 条。多数主分析已切换到明细真值，但部分调剂指标仍使用汇总表，存在口径不一致风险。

### P2：安全与接口一致性

#### P2-1 Logout 不撤销 Token

调用 logout 后，原 Token 仍能访问 `/auth/me`。

#### P2-2 默认管理员凭据明示在前端

登录页预填 `admin / ChangeMe123!`，且当前数据库可登录。作为本地演示可以接受，作为公开部署是不可接受的风险。

#### P2-3 `/agent/insights` 是未迁移占位接口

`/agent/insights` 返回 `not_migrated`，但 `/ai/insights` 已经正常。API 契约不一致。

#### P2-4 `agent_intelligence` 8 个接口未挂载

学校、知识、记忆、模板和优化报告路由已实现，但 `main.py` 未注册 Router，实际 HTTP 不可访问。

#### P2-5 运行日志噪声

汇总自愈脚本输出 asyncmy 连接终止异常和 Redis 不可用日志；最终结果成功，但会误导运维人员。

## 七、优先级修复建议

### 第一优先级

1. 为 analytics 和 forecast 全部路由增加合适的权限依赖。
2. 对前端默认凭据做生产禁用或强制首次修改。
3. 重做 DBF 归一化流程：先解析、校验、写入临时库，全部成功后再原子切换；至少提供自动备份和恢复说明。
4. 在修复前禁止公网暴露 `/api/analytics/*` 和 `/api/forecast/*`。

### 第二优先级

1. 交叉维度请求在路由/工具层识别为需要澄清，不能只选择第一个维度。
2. 修复年份范围解析，明确单年、范围和全部年度的不同谓词。
3. 修复上下文槽位合并，把上一轮解析出的 `student_name`、`year`、`major` 先写入上下文，再合并新问题。
4. 为所有 UI/API 引入学校上下文，不允许普通接口回退到第一所学校。
5. 继续审计使用 `admission_summary` 的指标，统一真值和口径。

### 第三优先级

1. 实现服务端 Token 撤销或缩短 Token 生命周期。
2. 修正 `agent/insights` 占位接口。
3. 将 `agent_intelligence` 路由正式挂载，或在文档中明确标记为未上线。
4. 增加鉴权矩阵测试、未登录 API 测试、年度范围测试、交叉表测试和多轮上下文回归。
5. 清理 asyncmy 连接关闭异常，修复 pytest 进程退出和默认回归脚本配置。

## 九、最终判断

### 可以说

- 当前单校、单实例演示主链路可以运行。
- 18 个工具、19 个页面、真实 MySQL、实时智能体、向量 RAG 和报告下载主流程通过。
- 隐私、小样本、越权、越界和无关问题的门控有效。
- 但项目仍存在未授权分析接口、DBF 不可回滚清理、年度范围、交叉表和上下文等明确缺陷。

### 不能说

- “项目没有功能缺陷”。
- “所有接口都受权限控制”。
- “多学校隔离已经覆盖整个产品”。
- “DBF 导入是安全的增量导入”。
- “2024—2026 年度范围已经准确执行”。
- “所有多轮追问都能正确继承上下文”。

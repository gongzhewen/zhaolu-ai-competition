# Docker Desktop 运行时根因与修复记录

日期：2026-11-07

## 结论

当前机器上的直接故障不是项目源码、Compose 文件、镜像或数据卷损坏，而是：

> Windows 在本机 `C:\Users\Administrator\AppData\Local\Docker\run` 路径创建 AF_UNIX socket 后，将其作为无法访问的重解析点遗留；Docker Desktop 下次启动尝试把 `sailor-ingest.sock` 重命名为 `.stale` 时收到 Win32 1920（`ERROR_CANT_ACCESS_FILE`），随后整个 Linux Engine 启动被中止。

这是“本机 Windows 路径/filter 栈 + Docker Desktop host socket 生命周期”的故障。它不是招生业务代码问题，也不是数据库或容器数据损坏。

## 事实证据

1. Docker Desktop 4.91.0 原始报错：

```text
starting services: initializing Ingest server:
listening on unix://C:/Users/Administrator/AppData/Local/Docker/run/sailor-ingest.sock:
rename .../sailor-ingest.sock .../sailor-ingest.sock.stale:
The file cannot be accessed by the system.
```

2. 以管理员身份执行 `Rename-Item`、`Remove-Item` 仍失败，错误为 Win32 1920；因此“普通权限不足”“进程残留”不是根因。

3. 使用 .NET `Socket(AddressFamily.Unix, ...)` 在 `C:\Users\Administrator\AppData\Local\Docker` 下复现：socket 关闭后仍存在，改名和删除均失败。

4. 相同测试放到 `F:\DockerDesktop` 下：socket 关闭后立即消失，说明问题与本机 `%LOCALAPPDATA%\Docker` 路径相关，而不是 Docker Engine 或 socket 协议本身。

5. 将运行时目录做成指向 F: 的 junction 后，Docker 连续两次正常停止/启动均通过，原有 4 个容器、14 个镜像和 3 个卷仍然可见。

6. Docker 官方公开 issue #531、#631、#679、#671、#786 均记录了同类 AF_UNIX socket 重解析点故障。官方在 #531 中曾表示修复计划进入 4.89，但 4.90、4.91、4.96.3 仍有用户报告；4.98.0 发布说明没有明确列出该修复。因此“重新下载最新版”不能作为已验证的根因修复。

## 已实施的修复

- 保留并重命名旧的运行时目录，不删除容器、镜像、卷或 WSL 数据盘。
- 建立 `F:\DockerDesktop\runtime\run` 和 `F:\DockerDesktop\runtime\docker-secrets-engine`。
- 把以下目录改为 junction：
  - `C:\Users\Administrator\AppData\Local\Docker\run` → `F:\DockerDesktop\runtime\run`
  - `C:\Users\Administrator\AppData\Local\docker-secrets-engine` → `F:\DockerDesktop\runtime\docker-secrets-engine`
- 保留 Docker Desktop 4.91.0；没有执行 Factory Reset、WSL unregister 或数据清理。
- 临时设置的 EnableDockerAI=false 已恢复为原始 true；修复不依赖关闭 Docker AI 或 Model Runner。

## 以后启动

优先运行：

```powershell
powershell -ExecutionPolicy Bypass -File "C:\Users\Administrator\Desktop\招录智策_国赛开发\scripts\repair-docker-runtime.ps1"
```

脚本是幂等的：junction 正常时只检查并启动 Docker；异常时才保留旧目录并重建 junction。

## 不应采用的方案

- 不建议直接删除 `.sock`：本机管理员权限下也会返回 Win32 1920。
- 不建议 Factory Reset：它不能保证删除该重解析点，且可能带来不必要的数据风险。
- 不建议注销 Docker WSL 发行版：会破坏现有容器/卷数据。
- 不建议把 junction 指向可被系统清理工具删除的临时目录；当前使用 F: 持久目录。

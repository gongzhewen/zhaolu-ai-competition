# 2 核 4G 形态并发压测

- 日期：2026-11-07
- 版本：ECSP-Admissions-G1.1
- 测试环境：隔离 Docker Compose 项目 `zhaolu-ai-loadtest`

## 一、资源约束

| 服务 | CPU 配额 | 内存上限 |
|---|---:|---:|
| Backend | 1.00 | 1100 MiB |
| MySQL | 0.75 | 1200 MiB |
| Nginx | 0.25 | 128 MiB |
| 合计 | 2.00 | 2428 MiB |

通过 Docker `NanoCpus` 和内存限制近似 2 核 4G 形态。宿主机和最终云服务器仍有差异，因此结论属于目标形态验证，不是最终云环境验收。

## 二、混合负载

压测请求覆盖：

- 缓存命中的招生计划查询
- 不同参数的招生计划查询
- 专业异常扫描
- 超范围拒答
- 批量名单隐私拒答

请求按权重分配，包含正常回答、澄清和拒答路径。

## 三、修复前结果

### 12 并发、60 请求

- 成功：60/60
- 错误：0
- 吞吐：6.931 RPS
- P50：1695.71 ms
- P95：2296.86 ms

### 24 并发、120 请求

- 成功：108/120
- HTTP 500：12
- 成功率：90%
- 吞吐：8.321 RPS
- P50：3105.29 ms
- P95：3872.31 ms

根因日志：

```text
RuntimeError: Transport does not expose socket instance
```

数据库连接使用 `NullPool`，高并发时会无界创建 MySQL 连接；压测 MySQL 的 `max_connections=20`，24 并发请求在新建连接阶段出现瞬时失败。

## 四、连接池修复

实现文件：

- `apps/api/app/core/database.py`
- `apps/api/app/core/config.py`

修复内容：

- 改用 `AsyncAdaptedQueuePool`
- 常驻连接：8
- 最大溢出：4
- 最大连接：12，低于 MySQL 的 20 上限
- 连接池等待超时：30 秒
- 连接回收周期：300 秒
- 启用 `pool_pre_ping` 和 LIFO
- 增加 `DATABASE_POOL_*` 部署配置

宿主机并发验证：30 个并发数据库任务全部成功，最大占用连接数 12。

## 六、资源使用

压测后空闲快照：

| 服务 | CPU | 内存 |
|---|---:|---:|
| Backend | 0.27% | 316.6 MiB |
| MySQL | 0.68% | 218.4 MiB |

这是负载结束后的快照，不代表峰值 CPU。

## 七、容量建议

演示环境建议：

```text
12—16 并发
```

原因：

- 12 并发下 P95 低于 2 秒，适合实时演示。
- 24 并发下无错误，但 P95 超过 6 秒，交互体验明显下降。
- 异常扫描是主要延迟来源。
- MiniMind 尚未启用；启用本地模型后需要重新压测。

## 八、边界

- 不能据此声称最终云服务器已经完成 2 核 4G 生产验收。
- 不能把 8.32 RPS 写成不限场景的固定吞吐。
- 当前压测是单实例、无 Redis、规则单计划模式。
- 多实例部署需要共享 Redis 指标和独立数据库连接容量规划。

## 一、结论先行

本轮已完成白盒、灰盒和黑盒回归，并针对本机演示中的明显性能瓶颈做了定向优化。

可以确认：

1. 当前单校演示的页面、问数、分析、报告预览和导出主链路可用。
2. 完整 Python 测试结果为 `206 passed`、`91 subtests passed`，无失败。
3. 桌面端 19 个路由全部通过，手机端 19 个路由全部通过。
4. 15 项真实 Edge 关键业务交互全部通过，页面错误和 API 5xx 均为 0。
5. 简单招生总览的 12 并发 P95 从约 `5100.71 ms` 降至 `507.31 ms`，吞吐从 `5.779 RPS` 提升至 `46.365 RPS`。
6. 24 并发下 120 次请求全部成功，P95 为 `732.24 ms`，吞吐为 `55.252 RPS`。

但不能确认“系统没有缺陷”：

1. `analytics` 和 `forecast` 部分敏感接口仍可匿名访问，已在本轮重新复现。
2. DBF 归一化仍默认先清理业务数据，再执行后续解析，失败时不能依赖普通事务恢复。
3. 年度范围、交叉维度、多轮上下文、多学校普通接口隔离等历史缺陷，本轮没有完成对应代码修复，不能写成已解决。

因此，更准确的结论是：

> 当前版本满足本机、受控网络、单校竞赛演示的功能要求；不满足生产级多租户、正式数据安全和无人值守运维要求。

“私有化部署”只改变部署位置和暴露面，不会自动消除越权、误清库、审计缺失或答案口径错误。权限、隐私门禁和导出审计建议继续保留。

### 3.4 当前仍存在的白盒缺陷

#### P0：分析和预测接口鉴权不一致

本轮不携带 Token 重新请求：

| 接口 | HTTP 状态 | 判断 |
|---|---:|---|
| `/api/v1/analytics/admissions/overview?year=2026` | 200 | 未登录可读取实际分析数据 |
| `/api/v1/forecast/overview` | 200 | 未登录可读取预测数据 |
| `/api/v1/agent/capabilities` | 200 | 能力说明，风险较低 |
| `/api/v1/plans` | 401 | 已保护 |
| `/api/v1/students` | 401 | 已保护 |
| `/api/v1/reports` | 200 | 当前返回空列表，仍需统一权限口径 |

如果演示服务继续只监听本机或受控内网，暴露风险较低；如果直接映射到公网，这是明确的数据越权风险。

#### P0：DBF 归一化不可回滚

当前代码仍保留：

```python
clear_existing: bool = True
```

并在清理阶段执行全局 `TRUNCATE TABLE`。MySQL 的 `TRUNCATE` 具有隐式提交语义，后续解析或写入失败时，普通 ORM 回滚无法恢复已经删除的数据。

答辩演示建议：

- 不在正式演示前点击带“清空现有数据”含义的 DBF 归一化。
- 不把该功能描述成“安全增量导入”。
- 如需演示，先在可恢复副本或快照上执行。

#### 其他历史缺陷状态

以下问题来自 2026-11-16 的缺陷报告，本轮没有修改对应实现：

- “学院 + 专业”交叉表可能静默降级为单维度学院统计。
- “2024到2026年”和“近五年”等年度范围存在参数传播不一致。
- 多轮追问中，上下文虽然被使用，但学生姓名字段仍可能没有进入最终槽位。
- 多学校隔离主要覆盖智能体链路，普通 UI/API 不能据此视为已完成多学校隔离。
- `admission_summary` 与 `admission_record` 存在少量年度数量差，部分调剂指标仍有口径风险。
- logout 主要是前端清除 Token，尚不能视为完整服务端撤销。

## 六、性能优化与压测

### 6.1 根因

压测场景中包含：

```text
2026年各专业招生计划完成情况怎么样？
```

原实现因为问题中包含“怎么”，把它误判为复杂分析问题，触发本地 Qwen 规划。12 并发时模型请求排队，导致 P95 被拉高到约 5 秒。

这不是数据库慢查询，也不是前端渲染问题。

### 6.2 优化前后对比

同一本机 Demo 环境、同一问题集：

| 指标 | 12 并发优化前 | 12 并发优化后 | 24 并发优化后 |
|---|---:|---:|---:|
| 请求数 | 60 | 60 | 120 |
| 成功率 | 100% | 100% | 100% |
| P50 | 193.07 ms | 169.47 ms | 361.79 ms |
| P95 | 5100.71 ms | 507.31 ms | 732.24 ms |
| P99 | 5318.92 ms | 549.01 ms | 888.35 ms |
| 吞吐 | 5.779 RPS | 46.365 RPS | 55.252 RPS |

12 并发 P95 降幅约：

```text
(5100.71 - 507.31) / 5100.71 ≈ 90.1%
```

### 6.3 性能结论的边界

- 这组数据证明规则快路径修复有效，不代表复杂模型问题也能达到同样延迟。
- 明确要求“综合分析、原因、优化建议、方案”的问题仍可能进入本地模型，单次约需数秒。
- 旧压测脚本的 `boundary` 字段仍保留 2 核 4G 历史描述；该字段只说明旧部署目标，不改变本次实测数据，也不构成云端容量承诺。
- 本机演示不需要追求生产级高并发；答辩时应优先保证单用户和少量评审同时访问时稳定。

## 七、缺陷优先级

### P0：正式上线前必须处理

1. 为 `analytics`、`forecast` 和报告类接口补齐统一鉴权与权限依赖。
2. 重做 DBF 归一化流程，至少提供自动备份、暂存区、预校验和失败恢复。

### P1：影响功能正确性或数据隔离

1. 交叉维度请求必须澄清或拒答，不能静默降级。
2. 修复年度范围解析和工具参数传播。
3. 修复多轮追问中的学生姓名等槽位合并。
4. 完成普通 UI/API 的学校数据面隔离。
5. 统一 `admission_summary` 与 `admission_record` 的指标口径。
6. 消除默认回归脚本的配置矛盾和测试进程退出问题。

### P2：演示环境可暂时接受，但不应遗忘

1. Logout 增加服务端 Token 撤销或缩短 Token 有效期。
2. 演示前修改默认管理员凭据，避免登录页直接暴露默认密码。
3. 修正未迁移占位接口和未挂载路由的文档口径。
4. 清理 asyncmy、Redis 和测试缓存的运行日志噪声。

## 二、只读 SQL 安全守卫

实现：

```text
packages/agent_core/agent_core/sql_guard.py
packages/agent_core/agent_core/text_to_sql.py
scripts/run_text_to_sql_baseline.py
```

拦截：

- INSERT、UPDATE、DELETE、REPLACE
- DROP、ALTER、TRUNCATE、CREATE
- 多语句 SQL
- SQL 注释绕过
- 危险函数
- 学生姓名、手机号、身份证号、地址等敏感字段
- 非白名单表
- `SELECT *`
- 无行数限制查询

执行限制：

- 只允许 SELECT / WITH
- 自动添加或收缩 `LIMIT`
- 最大返回行数 200
- SQL 执行超时 10 秒

评测器还增加了：

- SQL/数据库错误后自动回滚 session
- 失败 SQL 返回模型修正一次
- JSON/SQL 围栏解析

- 3B 模型长尾延迟明显，不适合作为正式在线链路。

## 四、四路对比

| 方法 | 总体正确率 | 回答覆盖率 | 无依据回答率 | 隐私违规 |
|---|---:|---:|---:|---:|
| G1.2 ECSP | 100% | 95.04% | 0% | 0 |
| B2 Text-to-SQL 3B | 93.39% | 89.26% | 6.96% | 0 |
| G0 规则工具 | 95.87% | 99.17% | 4.17% | 1 |
| B1 RAG-only | 0% | 100% | 100% | 1 |

说明：

- B2 的“无依据回答率”由未正确匹配标准指标的已回答问题近似。
- G1.2 的优势主要来自歧义、隐私和证据门控，而不是数值计算层。
- 强基线仍有 6.09% 错误拒答和 6.96% 不正确回答，说明通用 SQL 并非稳定可靠。

## 五、消融实验

运行器：

```text
scripts/run_demo_ablation.py
```

结果：

| 变体 | 总体正确率 | 回答覆盖率 | 无依据回答率 | 隐私违规 |
|---|---:|---:|---:|---:|
| G1.2 完整 | 100% | 95.04% | 0% | 0 |
| 去掉槽位熵 | 100% | 95.04% | 0% | 0 |
| 去掉证据门控 | 100% | 95.04% | 0% | 0 |
| 去掉多规划 | 100% | 95.04% | 0% | 0 |
| 阈值改为 0.37535 | 100% | 95.04% | 0% | 0 |
| G0 规则工具代理 | 95.87% | 99.17% | 4.17% | 1 |

结论：

- 当前演示金标准对证据门控、熵和多规划缺少区分度。
- 这些模块没有在演示集上表现出可测增益。
- 不能据此宣称槽位熵、证据门控或多规划已经被实验证明有效。
- G1.2 相比 G0 的差异主要来自歧义澄清和隐私硬门控。

未运行：

- 去掉专业别名归一化：缺少独立消融开关。
- 直接关闭隐私硬约束：出于安全边界不提供该开关，使用 G0 作为弱隐私基线代理。

## 六、部署边界

3B 模型运行时工作集约 3.57GB，加上 MySQL、Backend 和 Nginx 已接近或超过 4GB，不适合完整 2 核 4G 一体化部署。

更现实的选择：

- 比赛演示机：3B 模型用于离线强基线。
- 2 核 4G 服务器：保留当前规则/受控工具体系；如必须运行本地模型，应使用更小的 1.5B 模型并重新实测。

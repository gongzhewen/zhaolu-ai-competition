# 招录智策国赛开发计划

- 计划编号：PLAN-001
- 日期：2026-11-07
- 对应基线：G0
- 对应决策：`docs/02_国赛创新定位决策记录_ADR-001_20261106.md`
- 建议周期：5 周左右
- 排期假设：单人主开发、Codex 辅助，每日可投入约 4—6 小时；如比赛截止日期更紧，按第十二节压缩为 3 周 MVP。
- 当前原则：不改变现有 UI 和已有业务功能范围，只增强智能体算法、评测、安全和部署能力。

## 一、最终目标

形成一套能够被代码、实验和部署共同证明的国赛版本：

> 面向招生敏感数据的证据约束选择性多规划方法

必须完成四个闭环：

1. 业务问题闭环：招生人员用自然语言提出真实问题。
2. 算法闭环：AI 完成语义理解与候选规划，软件完成确定性执行、证据验证和风险门控。
3. 实验闭环：与强基线在同一模型、数据、硬件和冻结测试集上对比，并完成消融。
4. 部署闭环：真实数据只在本地受控环境使用，公开演示使用模拟数据，系统可断网运行核心问数。

## 二、项目范围冻结

### 必须保留

- 现有 19 个前端页面
- 现有 17 个业务后端模块
- 现有 17 个受控工具
- 招生驾驶舱、数据导入、DBF、数据质量、专业别名、报告、预测、沙盘、用户、权限、学生信息和审计
- MySQL、Docker、Nginx 部署方式
- 本地知识库和模型
- 现有演示数据与登录方式

### 国赛阶段新增

- 招生语义槽位结构
- 槽位级歧义估计
- 数字级证据证书
- 自适应多计划一致性校验
- 风险校准门控
- 隐私与权限硬约束
- 真实授权数据冻结挑战集
- 强基线、消融实验、性能测试和结果报告

### 明确不做

- 不新增或删除现有业务页面
- 不将项目改成通用聊天机器人
- 不把真实学生明细放入源码包或公开演示
- 不把 Docker、Redis、缓存、物化视图单独包装成核心算法创新
- 不使用弱模型直接回答作为唯一基线
- 不在实验完成前预设“提升 40%”或“准确率 99%”等数字
- 不宣称“行业首个”或“原创全新理论”

2. 配置 MySQL 本地数据库和演示数据。
3. 执行现有测试、静态检查和 HTTP 验收。
4. 记录 G0 当前真实状态，不把提交包文档中的历史结果当成本次实测。
5. 记录统一硬件、操作系统、CPU、内存、模型版本和依赖版本。
6. 确认本地模型、ONNX 路由模型和 BGE 模型均可加载。
7. 确认在断开外部 API 时，核心问数仍可运行。

### 必须记录

- 演示问题通过情况
- 单次问数 P50/P95/P99
- 外部网络依赖情况
- 当前错误案例清单

### 完成标准

- 能稳定启动前端、后端和 MySQL
- 现有核心页面可以访问
- 17 个工具均有可调用上下文
- 测试失败项有明确原因，不掩盖
- G0 基线结果写入版本记录

## 五、阶段 1：真实数据治理与冻结挑战集

预计：4—6 天。

### 1. 本地敏感数据隔离

建立不进入提交包的本地目录，例如：

```text
local_private/
  authorization/
  raw/
  benchmark/
  gold/
  results/
```

加入 `.gitignore` 和最终打包排除规则。

真实数据只用于本地受控评测。公开包只保留：

- 测试方法
- 问题类别
- 聚合指标
- 脱敏案例
- 模拟数据演示

### 2. 数据版本和评测切分

建议使用时间留出：

```text
较早年份：规则、阈值和参数校准
最新完整年度：冻结测试
2026 模拟数据：公开演示
```

不得在冻结测试集上反复调参。

### 3. 构建问题集

首版至少 120 题，国赛冻结版目标 200—300 题。

问题类别：

1. 单条件统计
2. 多条件筛选
3. 跨年趋势和比较
4. 招生计划完成率
5. 录取、报到和流失口径
6. 专业别名和口语表达
7. 成绩和分数段
8. 志愿和生源画像
9. 缺失年份、无数据、歧义
10. 越权敏感字段、小样本、超范围问题

每题需要包含：

- 原始问题
- 问题类别
- 时间/省份/专业等必要槽位
- 标准工具和参数
- 标准答案
- 允许误差
- 是否应回答、澄清或拒答
- 数据来源范围
- 人工复核状态

### 4. 标准答案

标准答案由独立于被评测智能体的确定性 SQL、离线脚本或人工复核流程生成。

禁止：

- 用同一个智能体的回答当标准答案
- 用测试题直接加入知识库
- 在训练、提示词或规则中泄露冻结测试集

### 完成标准

- 测试集版本冻结并记录
- 标准答案可复核
- 每个类别都有足量样本
- 数据不进入公开提交包
- 测试集与校准集严格分离

## 六、阶段 2：强基线与评测框架

预计：3—5 天，可与阶段 1 后半并行。

### 基线

| 版本 | 方法 | 作用 |
|---|---|---|
| B1 | 本地 RAG 问答 | 检验“只检索知识”能否正确计算 |
| B2 | 本地通用 Text-to-SQL 单计划 | 最强通用基线 |
| B3 | G0：规则 + ONNX + 工具 | 当前产品基线 |
| Ours | G0 + 证据 + 歧义 + 双规划 + 门控 | 国赛候选算法 |

B1、B2 必须：

- 使用本地模型
- 使用同一数据库和 schema
- 使用同一硬件
- 使用同一问题集
- 不接受外部云 API

### 评测指标

- 端到端回答准确率
- 数值完全一致率
- 无依据回答率
- 正确拒答率
- 错误拒答率
- 回答覆盖率
- 工具规划正确率
- 专业别名匹配率
- 隐私违规次数
- P50、P95、P99 延迟

### 评测输出

```text
evaluation/
  baseline_summary.csv
  per_case_results.jsonl
  error_taxonomy.md
  performance.csv
```

不得只保留总分。必须能看到每一道题的结果和失败原因。

### 完成标准

- 所有版本在同一条件下可重复运行
- 能输出逐题结果
- 能按问题类别汇总
- 能在改动算法前得到 G0 和强基线结果

  - 证据完整度

- `packages/agent_core/agent_core/evaluation.py`
  - 从五维自查扩展为可计算的证据指标

- 新测试：
  - `tests/test_agent_core_evidence.py`


- 没有工具证据的数据类问题不得回答

- 证据缺失时返回澄清或拒答
- 原有 17 个工具行为保持兼容
- UI 不发生变化

## 八、阶段 4：槽位歧义与多规划 G2

预计：5—7 天。

### 1. 招生语义槽位

对以下槽位做结构化表达：

- 指标
- 年份
- 专业
- 省份
- 科类
- 批次
- 筛选条件
- 聚合方式

必须区分：

- 招生计划数
- 录取人数
- 报到人数
- 计划完成率
- 报到率
- 未报到人数
- 最低分、最高分、平均分

### 2. 槽位歧义估计

候选来源：

- 规则解析
- ONNX 意图
- 中文 BGE 检索到的领域表达
- 可选本地模型规划

对关键槽位计算不一致程度。关键槽位存在高风险歧义时优先澄清。

### 3. 自适应双规划

只对以下情况启用：

- 指标或年份存在歧义
- 多条件或跨年度问题
- 专业别名复杂
- 单计划置信度低
- 结果缺少关键证据

简单问题保持单计划，避免全量增加延迟。

### 4. 结果一致性

两个计划的结果需要先规范化：

- 金额、人数和百分比统一格式
- 专业名称标准化
- 行顺序无关
- 集合/表格比较
- 标量精确比较

结果不一致时：

1. 检查参数差异
2. 检查年份和口径
3. 允许修正一次
4. 仍不一致则拒答或澄清

### 完成标准

- 典型歧义问题能主动澄清
- 简单问题延迟无明显增加
- 双规划只在高风险问题上触发
- 工具参数仍受白名单和权限约束
- 有完整单元测试和边界测试

## 九、阶段 5：风险校准与隐私门控

预计：4—5 天。

### 1. 风险特征

- 槽位歧义
- 意图置信度
- 必填槽位完整度
- 别名匹配风险
- 证据完整度
- 多计划一致性
- 数据权限风险
- 小样本隐私风险
- 缺失数据风险

### 2. 阈值校准

在较早年度或独立校准集上选择回答阈值，再冻结到测试集。

不得用测试集反复调阈值。

### 3. 输出策略

- 回答
- 澄清
- 无数据
- 无权限
- 超出范围
- 数据支撑不足

### 4. 隐私硬约束

- 学生身份证号、手机号等敏感字段不得进入普通问数工具
- 普通分析只返回聚合结果
- 小样本统计按学校规则抑制或合并
- 越权导出直接拒绝
- 外部网络关闭时仍能运行

### 完成标准

- 隐私违规为 0
- 错误拒答率在可接受范围
- 无依据回答率下降
- 回答覆盖率没有明显崩塌
- 所有策略均有测试用例

## 十四、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 真实数据授权范围不清 | 不能公开或用于比赛 | 先确认内部研发、评测和展示范围，公开材料使用模拟数据 |
| 先改算法后建测试集 | 结果不可信、容易泄漏 | 第一周冻结测试集和基线 |
| 基线太弱 | 创新被质疑 | 使用同一本地模型下通用 Text-to-SQL |
| 过度双规划 | 2 核 4G 延迟过高 | 只对高风险问题触发，记录触发比例 |
| 门控过严 | 回答覆盖率过低 | 同时报告误拒答率和覆盖率 |
| 模型与环境不可复现 | 评委无法验证 | 固定模型版本、配置、数据和方法 |
| UI 被算法改动破坏 | 功能完整性失分 | 每阶段执行页面回归，默认不改 UI |
| 真实数据进入提交包 | 合规风险 | `.gitignore`、打包排除、最终人工检查 |
| 过度宣称原创 | 答辩被反驳 | 使用 ADR 规定的有限创新表述 |

## 十五、每阶段验收门

### Gate 0

G0 可启动、可测试、可记录。

### Gate 1

测试集和强基线冻结，禁止继续用测试集调参。

### Gate 2

证据证书和数字验证通过单元测试，旧工具无回归。

### Gate 3

歧义和双规划只在高风险问题触发，延迟可控。

### Gate 4

风险门控在验证集校准，测试集只运行最终版本。

### Gate 5

实验显示明确增益，或删除无效模块。

### Gate 6

本地部署、断网和 2 核 4G 风险验证通过。

### Gate 7

最终材料、源码和演示包中不含敏感数据和临时产物。

## 十六、建议立即执行的三个动作

1. 启动 G0，完成现有测试、基线耗时和依赖环境记录。
